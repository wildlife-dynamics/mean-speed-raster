Technical Guide

What each step of spec.yaml does and with which settings, how the raster is built, how views and files reach the dashboard, and how to recompile and test.

Pipeline

EarthRanger observations
  → relocs (bad-coordinate filter) → trajectory (segment filter) → temporal index → map_columns
  → split_groups ── per view ──→ ecograph grid → sort → classify → colour → GeoJSON layer ─┐
                                      │                                  view state ──────┤
                                      └→ persist GeoParquet → files view      draw map → persist HTML → map widget
                                                                     ↓                                   ↓
                                                         gather_dashboard  ←  merge_widget_views  ←──────┘

Steps after split_groups run once per view: the All view, or one view per subject. The task defaults skip a step when its input is an empty table or a step it depends on was skipped (any_is_empty_df, any_dependency_skipped). The map widget is the exception, set to never skip, so an empty view still gets a widget.

How the raster is built

  1. The grid's cell size is resolution if set (it is null here), else step_length (form, default 2000 m), else the mean of dist_meters (the form's Auto option sends null).
  2. The grid covers the view's tracks in their UTM zone, padded by one cell.
  3. Each segment's speed_kmhr is credited to the cell where the segment starts. With tortuosity_length: 3, the last two segments of each subject's track are not credited.
  4. Each cell's value is the mean of its segments' speeds, first per subject and then across subjects (interpolation: mean). Cells with no segments are left out.
  5. The raster is written to an in-memory GeoTIFF and read straight back as square polygons: one row per cell, with columns value and geometry.

Why sort before classifying

apply_color_map hands out colours in the order the class labels first appear in the table. Without sorting, the first cell (wherever it happens to be) took the first colour, so the legend's ranges and colours came out scrambled. Sorting by value ascending makes the lowest class appear first. The colour ramp then runs in class order: dark green for the slowest class through to red for the fastest.

How views and files reach the dashboard

The grouped steps return lists of (view key, value) pairs. Two wiring rules matter:

  • Steps that need the view key use map with argnames: [view, …]. That covers files_single_view and ecograph_widget. With mapvalues, the key isn't passed in, so every file view had view = None.
  • gather_dashboard runs once, with files: ${{ workflow.files_single_view.return }} in partial. It accepts a list of file views and merges them by view key. Using mapvalues over files here produced one dashboard per subject, a list the runner can't display. That's why an earlier run had outputs but no dashboard.

gather_dashboard asserts that every file view key is None or one of the widget view keys, so the files and widgets must come from the same split_groups output.

Metadata and thumbnail

spec.yaml's metadata block (name, description, maintainer, licence, keywords) is what the template catalogue shows. metadata.thumbnail points to resources/thumbnail.png (2560×1440, under the 5 MB limit). The thumbnail uses synthetic data: a made-up 120-day, 3-hourly random-walk track that alternates slow and fast bouts. It runs through this spec's own steps (trajectory, ecograph at 2000 m, sort, classify, colour, layer, map) and is screenshotted in headless Chrome. Don't replace it with a screenshot of real subjects' data.

Recompiling

spec.yaml is the source; ecoscope-workflows-mean-speed-raster-workflow/ is generated from it by wt-compiler.

./dev/recompile.sh --update   # keeps the lock file and bumps VERSION.yaml
./dev/recompile.sh --install  # a new lock file, and the packages installed

Both use --clobber, which deletes the generated folder including its .pixi environment. Run pixi install in ecoscope-workflows-mean-speed-raster-workflow/ before running anything from it again.

This repo is also compiled from an EcoWorkbench design. EcoWorkbench rewrites spec.yaml from the design each time it compiles the repo. If you edit spec.yaml by hand, re-import it into the design (or make the same edits there) before compiling from EcoWorkbench, or the hand edits are lost. README.md and docs/ are only written once and are safe to edit.

Testing

Each case in test-cases.yaml runs the workflow with its settings:

pixi run --manifest-path pixi.toml -e default bash dev/pytest-cli.sh mean_speed_raster --all
